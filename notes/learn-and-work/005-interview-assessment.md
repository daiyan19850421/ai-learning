## 三、逐题点评

### A. 项目（强）

**A2–A3**  
- 场景清晰：高速/钻井/应急 + 音视频调度。  
- 技术栈 **Java + FreeSWITCH** 是 **可售卖的垂直能力**，北京有政企、交通、能源、融合通信类 JD。  
- 同步慢案例：**双缓冲（A/B 表）+ Redis 标记当前表** 是成熟思路，说明有 **生产权衡** 能力（第三方不可改 → 改自己的读写路径）。  
- **不足**：未提指标（原来多少秒 → 现在多少秒）；面试建议补数字。

**A4–A5**  
- 标签表设计 + 统计 + 查询性能：**与「客户洞察」一致**。  
- **十几亿行** + 维度复杂无法直接查 → **离线/定时汇总到新表**：这是 **数据工程化** 正路，不是偷懒。  
- **不足**：未体现 `EXPLAIN`、索引设计细节；优化发生在 **架构层（预计算）** 而非 **SQL 层**，与 C 节表现一致。

### B. Java（弱，与 10 年不匹配）

| 题 | 你的答案 | 评估 |
|----|----------|------|
| B1 事务自调用 | 不清楚 | **高级岗必失分**；实际工作可能少写事务或靠框架默认 |
| B2 上千路上报 | 不清楚 | 调度系统相关却无思路，**与 A2 形成反差**（可能并发在 FreeSWITCH/ C 层，Java 侧重配置与集成） |
| B3 并发工具 | 没用过 | **强烈暗示**：Java 侧以 **业务逻辑 + 集成 + 数据** 为主，非高并发中间层 |

**推断（非指责）**：你的 10 年价值主要在 **领域 + 集成 + 数据方案**，不在 **JVM 并发与 Spring 深度**。投岗应 **扬长避短**。

### C. MySQL（中等偏下）

**C1 标准答案（InnoDB 联合索引 (a,b,c)）**：

| SQL | 你的答案 | 正误 |
|-----|----------|------|
| `WHERE a=1 AND b=2` | 能 | ✓ |
| `WHERE b=2 AND c=3` | 印象能 | ✗ 一般 **不能**（缺最左列 `a`） |
| `WHERE a=1 ORDER BY b` | 估计不能 | ✗ 一般 **能**（先按 `a` 过滤，再按 `b` 有序） |

**C2**：代码 → 索引 → 执行计划，**顺序合理**，但偏泛；结合 A5，你 **更习惯用预聚合解决「查不动」**，而非慢 SQL 微调。

### D. 系统设计（弱）

调度 ACK/超时重试答「不清楚」，而主项目即调度域 —— 可能 **协议与状态机在 FreeSWITCH/设备侧**，Java 未参与该层。  
**对外叙事**：强调 **拨号计划、设备/用户、FS 集成**；**勿包装成「分布式任务调度架构师」**。
