# Staff 一周时间分配：交给 AI vs 必须自己 retain

## 前置

- 背景：[002-java.md](./002-java.md) 职业阶梯与 Staff 能力分析
- 目的：在 AI 压缩执行层的前提下，明确 **哪些活可以交出去、哪些活必须留给自己**——避免两种极端：「什么都自己写」和「什么都丢给 AI」

---

## 总原则

| 原则 | 说明 |
|------|------|
| **AI 做初稿与放大器** | 调研、样板代码、文档骨架、测试数据、日志摘要 |
| **人做判断与签字** | 选型取舍、上线/回滚决策、事故定界、跨团队承诺、指标定义 |
| **Retain = 别人无法替你对后果负责的部分** | 不是「更难的手活」，而是「责任 + 上下文 + 信任」 |
| **每周固定比例（参考）** | 执行层 ≤ 40% 且其中 ≥ 50% 用 AI 辅助；责任层 + 组织层 ≥ 50% |

---

## 一周时间块概览（Staff 典型 40h）

| 时间块 | 占比（参考） | 主归属 |
|--------|-------------|--------|
| 深度工作与攻坚 | 25–35% | 人 retain（AI 辅助） |
| 设计 / RFC / 评审 | 15–20% | 人 retain（AI 写初稿） |
| 跨团队沟通与推动 | 15–25% | **人 retain** |
| Code / 配置 / 脚本 | 10–20% | **可大量交 AI** |
| 文档 / Runbook / 复盘 | 10–15% | 混合 |
| 学习与调研 | 5–10% | **可大量交 AI** |
| 事故与 on-call | 0–15%（不定） | **人 retain** |

---

## 分项清单：交给 AI / 必须 retain

### 1. 调研与学习

| 任务 | 交给 AI | 必须 retain | 说明 |
|------|---------|-------------|------|
| 新框架 API 概览、版本差异 | ✅ | | 让 AI 汇总 Release Notes、对比表 |
| 「在我们栈里是否可行」 | | ✅ | 要结合现有 Spring 版本、网络隔离、合规 |
| 读 PG / Spring AI 官方文档 | ✅ 辅助 | ✅ 终审 | AI 可能漏版本约束或幻觉引用 |
| 竞品 / 业界方案扫描 | ✅ | | 快速 breadth |
| **选型结论** | | ✅ | 写 ADR，签字 |

**实操**：调研用 AI 出「对比表 + 风险列表」；你补一节 **「在本公司的结论与不做清单」**。

---

### 2. 设计与 RFC

| 任务 | 交给 AI | 必须 retain | 说明 |
|------|---------|-------------|------|
| RFC 结构、背景段落、备选方案枚举 | ✅ | | 省起草时间 |
| 数据流 / 序列图初稿 | ✅ | | 再人工改边界与失败路径 |
| **失败模式与降级策略** | 部分 ✅ | ✅ | AI 常漏你们历史事故类 case |
| **容量与成本估算** | ✅ 算式 | ✅ 假设 | QPS、Token 单价、连接数假设需你定 |
| **跨团队影响面** | | ✅ | 谁改接口、谁值班，AI 不知道 org chart |
| 评审会议上的答疑与拍板 | | ✅ | |

**实操**：RFC 模板固定为「AI 填 1–4 节草稿 → 你写 5–7 节：决策、迁移、回滚、开放问题」。

---

### 3. 编码与实现

| 任务 | 交给 AI | 必须 retain | 说明 |
|------|---------|-------------|------|
| CRUD、DTO、样板测试 | ✅ | | |
| Spring AI / LangChain4j 集成脚手架 | ✅ | | 你 Review 版本与依赖 |
| **核心路径：事务边界、幂等、权限** | 部分 ✅ | ✅ | 必须人工 Review + 测试 |
| **Agent 工具调用与鉴权** | | ✅ | 越权、Prompt 注入不可交给 AI 自审 |
| 性能热点路径（连接池、批处理） | 部分 ✅ | ✅ | AI 不懂你们真实负载 |
| **上线前的最终 Merge 责任** | | ✅ | |

**实操**：让 AI 写「非核心模块」；**核心 20% 代码**（鉴权、计费、数据一致性）自己写或逐行 Review。

---

### 4. 数据库与数据层（PG / MySQL）

| 任务 | 交给 AI | 必须 retain | 说明 |
|------|---------|-------------|------|
| SQL 初稿、索引建议 | ✅ | | |
| `EXPLAIN` 结果解读辅助 | ✅ | | 贴 plan，让 AI 解释 |
| **是否加索引 / 是否改表结构** | | ✅ | 写锁、膨胀、业务窗口 |
| **生产变更执行与回滚** | | ✅ | |
| 慢查询治理优先级排序 | 部分 ✅ | ✅ | 结合业务 SLA |
| 备份 / PITR 演练结论 | | ✅ | 责任归属 |

**实操**：AI 出「索引候选 + 理论分析」；你跑 `EXPLAIN (ANALYZE, BUFFERS)` 并 **对变更窗口签字**。

---

### 5. AI 平台专项（RAG / Agent / 评估）

| 任务 | 交给 AI | 必须 retain | 说明 |
|------|---------|-------------|------|
| Chunk 策略、Prompt 模板试验 | ✅ | | 快速迭代 |
| Golden set 题目初稿 | ✅ | | |
| **评估指标定义（什么叫上线）** | | ✅ | 命中率、拒答率、成本上限 |
| **幻觉 / 越权 case 分类与处置** | 部分 ✅ | ✅ | 合规与安全 |
| 评估跑批与报表 | ✅ 脚本 | ✅ 解读 | AI 跑；你判断 regression |
| 模型 / 路由切换决策 | | ✅ | |
| 向业务解释「为何不能自动放开写操作」 | | ✅ | |

**实操**：建立固定 pipeline——**AI 跑 eval → 人看 diff 与 failure case → 人决定是否发布**。

---

### 6. 可观测、事故与 on-call

| 任务 | 交给 AI | 必须 retain | 说明 |
|------|---------|-------------|------|
| 日志聚合、异常聚类摘要 | ✅ | | |
| Runbook 模板、检查清单 | ✅ | | |
| **P0/P1 定界与指挥** | | ✅ | 谁回滚、谁对外同步 |
| **根因结论与系统性改进项** | 部分 ✅ | ✅ | 复盘会签字 |
| 告警阈值「最终定值」 | | ✅ | 误报/漏报 trade-off |
| 对管理层 / 客户的口径 | | ✅ | |

**实操**：on-call 时 AI 当 **copilot 查日志**；**回滚与对外声明**必须人做。

---

### 7. Code Review 与标准制定

| 任务 | 交给 AI | 必须 retain | 说明 |
|------|---------|-------------|------|
| 风格、明显 bug、样板问题 | ✅ | | |
| **架构一致性、团队规范** | | ✅ | 标准是你定的 |
| 培养 Junior（为什么这样改） | | ✅ | 信任与成长 |
| 「这类 PR 以后默认怎么做」→ 写入规范 | | ✅ | Staff 产出 |

**实操**：AI 做第一轮 Review；Staff 只盯 **边界、安全、可观测、与 RFC 一致性**。

### 8. 跨团队沟通与组织层

| 任务 | 交给 AI | 必须 retain | 说明 |
|------|---------|-------------|------|
| 邮件 / 消息初稿 | ✅ | | |
| 会议 agenda、纪要 | ✅ | | |
| **资源争取、排期谈判** | | ✅ | |
| **推动其他团队改接口 / 配合灰度** | | ✅ | 信用账户 |
| 与产品定 MVP 边界 | | ✅ | |
| 1:1 辅导、绩效相关反馈 | | ✅ | |

**实操**：AI 写「礼貌版催办邮件」；**是否升级、是否 escalate** 自己判断。

## 按星期几分配（可执行模板）

假设标准工作周；on-call 周把「深度工作」压缩，「事故」上浮。

| 日 | 建议重点 | AI 用法 |
|----|----------|---------|
| **一** | 对齐优先级：与产品/平台同步本周目标 | AI 整理 backlog、风险列表 |
| **二** | 深度攻坚 3–4h（性能 / 评估 / 难题） | AI 辅助查资料、写 POC 分支 |
| **三** | RFC / 设计评审；跨团队会议 | AI 出 RFC 初稿、纪要 |
| **四** | Review + 指导 Senior；推进规范落地 | AI 第一轮 CR |
| **五** | 文档、Runbook、eval 回归；周复盘 | AI 写文档骨架；**你写结论与下周决策** |

**Retain 硬块（日历上先占位，不被会议挤掉）**：

- 每周 ≥ 1 次 **eval / 压测 / EXPLAIN** 类「有数字的验证」
- 每周 ≥ 1 次 **跨团队** 推进（不是只发邮件）
- 每两周 ≥ 1 次 **复盘或规范更新**（哪怕 half page）

---

## 自检：你是否在 retain 该 retain 的事

每周五花 15 分钟勾选：

- [ ] 本周有 **至少 1 个我签字的技术决策**（不是仅合并 AI 生成的 PR）
- [ ] 本周有 **至少 1 个可引用的数字**（延迟、命中率、连接数、成本）
- [ ] 本周 **跨团队** 推进有明确结果（对方承诺或拒绝及原因）
- [ ] 没有把 **鉴权、上线门槛、事故结论** 完全交给 AI 未审
- [ ] 用 AI 省下的时间，投到了 **责任层/组织层** 而非刷更多 Demo

若连续 2 周只有「AI 帮忙写代码」、没有签字决策——说明正在滑向 **可替代的执行层**。

---

## 与两条职业路径的对应

| 路径 | 最该 retain 的 3 件事 |
|------|----------------------|
| **PG / 可靠性 Staff** | 变更窗口与回滚签字；慢查询优先级；事故根因与系统性改进 |
| **AI 平台 Staff** | 评估上线门槛；Agent 工具权限；模型/路由切换与成本责任 |
| **叠加** | RAG 数据层：检索 SLA + SQL 变更 + eval 发布 **同一人负责闭环** |

---

## 一句话

**交给 AI：初稿、样板、扫描、跑批。**  
**必须 retain：选型、签字、定界、推动、定义什么叫好、对线上后果负责。**  
Staff 的周历应让后者占 **不少于一半** 的刻意时间，而不是被前者的效率「无限扩容」挤没。
