## 学习目标

学完并完成练习后，你应能：

1. 说明：同样的任务，为什么「随口一问」和「结构化提问」会产生稳定程度不同的结果。
2. 独立写出一份包含 **角色 / 任务 / 约束 / 上下文 / 输出格式** 的 Prompt，并说明每一段各自解决什么问题。
3. 对 AI 的回复做一次有依据的校验（对照约束与输出格式），而不是直接采纳。
4. 用同一任务做至少两轮迭代：改 Prompt → 对比结果 → 记录哪一处改动改善了什么。

## 建议掌握的核心概念

阅读权威文档时，请主动提取并记下下列概念（名称以各文档原文为准，含义对齐即可）：

### 1. Prompt 不是聊天闲聊，而是任务规格

把一次有效提问拆成可检查的部件，而不是一句模糊需求。常见部件：

- **角色（Role）**：模型以什么身份、什么能力边界作答。
- **任务（Task）**：要完成什么；成功标准是什么。
- **约束（Constraints）**：禁止做什么、必须遵守什么（语言、长度、技术栈、是否可猜测等）。
- **上下文（Context）**：完成任务所必需的输入材料（代码片段、报错、需求原文、已有约定）。
- **输出格式（Output format）**：结构、字段、是否需要步骤、是否只要结论。

目标不是把 Prompt 写得很长，而是让每一段信息都有明确用途；缺哪一段，失败模式往往就能对上。

### 2. 结构化与分隔

主流厂商文档都强调：用清晰分隔（Markdown 标题、列表、XML 风格标签等）把指令、数据、示例分开，降低模型把「示例里的内容」当成「要执行的指令」、或把「用户数据」当成「系统规则」的概率。

练习时重点体会：

- 指令放哪里、数据放哪里。
- 多段约束是否互相矛盾。
- 示例（few-shot）是在示范格式，还是在偷偷引入新规则。

### 3. 具体优于抽象；可验证优于「感觉更好」

把「写得好一点」「专业一些」这类不可验证的要求，改成可检查的条件，例如：

- 输出必须包含哪些字段。
- 若信息不足，必须列出缺失项并停止猜测。
- 代码必须通过哪些检查（能否编译、是否改动指定文件、是否保留现有行为）。

### 4. 迭代是常态

Prompt 工程是迭代过程：先有一个能跑的版本，再针对失败模式改一处、测一处。记录「改了什么 → 结果如何变化」，比收藏大量「万能模板」更有用。

### 5. 先会判读，再谈效率

L1 的风险是「无法分辨对错」。本篇练习必须包含：**先对照你自己写的约束与格式检查输出，再决定是否采用**。这是从「工具人」迈向可控使用的必要条件。

## 实践任务（必须完成）

任选一个你真实遇到过的研发场景（修 bug、写单测、重构小函数、写接口说明均可），完成下面四步。

### 任务 A · 反例 → 正例

1. 先写一条你平时会随口发出的短 Prompt（反例）。
2. 再写成结构化 Prompt（正例），至少包含：角色、任务、约束、上下文、输出格式。
3. 用同一模型各跑一次，把两次完整输出贴进笔记（可脱敏）。

### 任务 B · 校验清单

对「正例」的输出，按你自己写的约束逐条打勾或打叉，至少回答：

- 哪些约束被遵守了？
- 哪些约束被违反或被忽略了？
- 有没有「看起来合理但你无法验证」的内容？你怎么处理的？

### 任务 C · 一轮定向迭代

只改 Prompt 中的 **一处**（例如收紧输出格式，或补上「信息不足时禁止猜测」），再跑一次，记录：

- 改动内容
- 结果变化
- 你是否更有把握采纳或拒绝该输出

### 任务 D · 自检问题（写入总结）

用自己的话回答（禁止大段摘抄原文）：

1. 结构化 Prompt 解决的是什么问题？解决不了什么问题？
2. 从 L1 突破点看，你现在是否比「复制粘贴 AI 代码」多了一步可操作的判断流程？那一步具体是什么？
